# التحقيق في تنفيذ Linux وبطاقات الأدوات — 27 أكتوبر 2026

## العطل المثبت

فُتحت طرفية حقيقية على خدمة Railway المنشورة من نسخة38، بهوية حساب التطبيق المعتادة، دون نموذج ذكاء اصطناعي أو تعديل مشاريع المستخدم. أعادت أدوات Bash الداخلية:

```text
UID=10001
ulimit -u: 48
/sys/fs/cgroup/pids.current=4
/sys/fs/cgroup/pids.max=1000
/bin/true: bash: fork: Resource temporarily unavailable
```

أُغلقت طرفية التشخيص وجلسة تسجيل الدخول المؤقتة. لم يكن السبب امتلاء حاوية Railway بألف عملية. السبب أن `RLIMIT_NPROC=48` الذي أضافه التطبيق حد للمعرّف الحقيقي للمستخدم، ويشمل خيوطه، وليس حدًا مستقلًا لكل طرفية. تعدد حاويات مزود الاستضافة لا يضمن نطاق UID مستقلًا. الاختبارات السابقة التي مررت `child_uid=None` لم تختبر إسقاط الامتياز إلى مستخدم الإنتاج؛ وعند UID0 لا يطبق Linux هذا الحد بالطريقة نفسها.

أزيل الحد المصطنع مع الإبقاء على حد PID الذي يطبقه مزود الحاوية، وخانة التنفيذ الواحدة، وانتهاء الطرفية، وإيقاف مجموعة العمليات، وحدود الملفات والذاكرة والخرج. لم تُرفع موارد الخدمة أو يُضف خادم جديد.

## البحث والقرار

المصادر المقروءة:

- [دليل Linux: getrlimit وRLIMIT_NPROC](https://man7.org/linux/man-pages/man2/getrlimit.2.html): يعرّف المحاسبة على مستوى real UID، وشمول threads، وفشل fork مع EAGAIN، واستثناء UID0.
- [Docker: ulimit وnproc](https://docs.docker.com/reference/cli/docker/container/run/#for-nproc-usage): يحذر صراحة أن nproc للمستخدم وليس للحاوية. حد PID على مستوى الحاوية هو الحد المناسب هنا.
- [OpenHands SDK ومعمارية Agent Server](https://github.com/OpenHands/software-agent-sdk): الأدوات والمحادثات والأحداث والعقود تظل نفسها، ويمكن تنفيذ مساحة العمل محليًا أو عن بعد. [Workspace](https://docs.openhands.dev/sdk/arch/workspace) يفصل واجهة مساحة العمل عن موضع التنفيذ.
- [E2B: تدفق أوامر التنفيذ](https://e2b.dev/docs/commands/streaming): stdout/stderr أثناء التنفيذ، ومعرّف أمر ونتيجة نهائية، وإعادة اتصال عند انقطاع العميل.
- [E2B: الأوامر الخلفية](https://e2b.dev/docs/commands/background): مقبض عملية يسمح بالانتظار/الاستعلام والإيقاف؛ انقطاع واجهة العرض لا يعني إعادة الأمر.

النتيجة المطبقة: يحتفظ ZEUS بواجهة المحادثة والأدوات الأصلية، وتصلها أحداث الخادم المهيكلة. اسم الأداة وعنوانها ومدخلاتها ونتيجتها وحالتها هي بيانات؛ لا يلزم تصميم بطاقات سحابية موازٍ. لم تُضف خدمة E2B مدفوعة أو حاوية OpenHands ثقيلة إلى Railway.

## تصحيح العرض والبروتوكول

مسار السحابة القديم عرف ثلاثة أنواع بطاقات فقط، وصنف `shell_execute` وغيره كـ`.info`، وهو سبب المستطيلات الصفراء. أصبح المحلي والسحابي يستخدمان `ZeusToolPresentation` ونفس `AssistantBlockView` و`ToolLiveSheet`. تنقل مدخلات JSON وعنوان `tool_title` كما في المسار الأصلي. تستخدم الموافقة البطاقة نفسها ولا تضيف رسائل «أرسلت الموافقة». يحذف إشعار السحابة المكرر داخل كل رد. يظهر خرج Bash داخل بطاقة الطرفية بدل ظرف JSON الخاص ببروتوكول الجلسة، وتبقى بيانات الجلسة للنموذج. الخروج غير الصفري يفشل بطاقة الأداة بالفعل.

ترسل الأوامر المتزامنة خرجها للبطاقة أثناء التشغيل بحد32ألف محرف وتحديثات محدودة، ثم نتيجتها النهائية. يستقبل العرض التفكير المرسل من المزود في نوعه الأصلي. تبقى موافقات المستخدم وحالة الخطأ الفعلية ظاهرة.

أضيف إصلاح محدود لخطأ مزود يطبع `tool_calls` كنص: لا يُنفذ النص مطلقًا. يطلب الخادم استدعاءً حقيقيًا للأداة المسجلة، ويضبط `tool_choice` وفق OpenAI Chat أو Responses أو Anthropic. بعد محاولتين يتوقف بخطأ واضح بدل ادعاء نجاح أو تكرار كتابة مجهولة. الأمثلة داخل prose أو fenced code لا تتحول إلى أوامر.

## التحقق

-29اختبار Python محلي ناجح، منها إصلاح بروتوكول فعلي عبر طلبات HTTP مصطنعة، عدم تنفيذ JSON النصي، رفض أسماء غير مسجلة، توقف الإصلاح بعد محاولتين، وحالة خروج Bash غير الصفرية.
-10اختبارات بوابة التخزين واختبارا محولات المصدر الأصلي ناجحة محليًا.
- صورة Docker تستخدم نفس ملف المتطلبات المقفل. اختبار مستقل داخلها يسقط الامتياز فعليًا إلى UID10001، مع60خيطًا إضافيًا لهذا المستخدم، وموارد0.25CPU/500MB/PID128. يجرب fork وpipeline وPython subprocess وكتابة/قراءة/حذف ملف؛ نجح. أضيف هذا الاختبار إلى CI، ولا يعتمد على وجود مفتاح نموذج. أُعيد تفعيل الحد48 في نسخة اختبار معزولة فقط؛ فشل الاختبار نفسه مع exit254 ورسالة fork، ثم نجح بالإصلاح.
- أضيف تحقق لأنواع البطاقات في اختبارات iOS، وواجهة تشخيص DEBUG تعرض البطاقات الأصلية بعناوين عربية لاستخراج لقطة من المحاكي. هذه ليست تجربة نموذج تجاري.

التحقق من نشر الإصلاح نفسه على Railway، وبناء IPA ولقطة البطاقات، يجب تسجيل نتيجته بعد تشغيل CI. نجاح الاختبارات المحلية وحده ليس إثباتًا لوصول الإصلاح إلى جهاز المستخدم. الأدوات التي تعتمد على الجهاز كمتصفحه أو المجلدات المرتبطة وعميل MCP الأصلي لا تعمل أثناء غياب الجهاز؛ نقل بقية عملاء التكامل إلى الخادم ما زال عملًا منفصلًا ولا يجوز وصفه بأنه مكتمل.
